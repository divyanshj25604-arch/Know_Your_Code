## 1. Deployment target: Render

| Criterion | What the code needs | Render |
| --- | --- | --- |
| Compatibility | One long-running Node process (Fastify, in-process job runner, worker threads), static client served by the same process, HTTPS | Native Node runtime (`runtime: node`) with build, pre-deploy and start commands; managed TLS; always-on paid web services |
| PostgreSQL | PostgreSQL ≥ 15 with `pg_trgm` and `pgcrypto` | Managed Render Postgres; the version is chosen per database (`postgresMajorVersion`) |
| Background jobs | In-process, durable state in Postgres; no queue service | Works in a web service as-is. No Redis or worker service needed |
| Persistent storage | None: tarballs are processed in temporary directories and all state is in Postgres | No disk needed, so zero-downtime deploys stay available. Render disables them when a persistent disk is attached |
| Cost | One small instance and one small database per environment | Paid instance plus paid database per environment. The free tier is unsuitable: free web services spin down after 15 minutes idle, and free databases expire after 30 days and have no backups |
| Maintenance | Infrastructure as code, managed backups, health checks | Blueprint (`render.yaml`); continuous backups with point-in-time recovery on paid databases; health checks that gate deploys |

**Alternatives considered:**

- **Fly.io:** needs a Dockerfile, and its managed Postgres is a separate product.
- **A VM with Docker:** we would operate backups, TLS and restarts ourselves.
- **Railway:** comparable to Render, but this repository has no Docker build and Render's Blueprint covers both the service and the database.

Render facts were taken from render.com/docs on 2026-11-12: `blueprint-spec`, `postgresql-backups`, `deploys`, `health-checks`, `free`. ## 2. Deployment configuration (`render.yaml`)

The file defines two environments, `kyc-staging` (branch `V1_KYC`, deploys on commit) and `kyc-production` (branch `main`, deploys manually), each with its own database (`kyc-staging-db`, `kyc-production-db`, PostgreSQL 17, `ipAllowList: []` so the database is reachable from Render services only).

| Requirement | How |
| --- | --- |
| Backend and frontend | One web service: `npm ci --include=dev && npm run build` builds `client/dist` and `server/dist`; `npm start` serves the API and the SPA from one origin, so web cookies stay first-party |
| PostgreSQL connectivity | `DATABASE_URL` from the database's internal connection string |
| Production configuration | `NODE_ENV=production` (the bundled server refuses anything else, P0.1), `TRUST_PROXY=true`, `NODE_VERSION=26` (the runtime all tests ran on), `DEPLOY_ENVIRONMENT` |
| Secrets | `COOKIE_SECRET` generated by Render; `ANTHROPIC_API_KEY`, prices, `GITHUB_TOKEN`, `ALERT_WEBHOOK_URL`, `APP_BASE_URL` are `sync: false`, so they are entered in the dashboard and never stored in the repository |
| Migrations | `preDeployCommand: node server/dist/db/migrate-cli.js`. A failing migration fails the deploy while the old version keeps serving. The server also migrates at start, under the same advisory lock |
| Health check | `healthCheckPath: /api/v1/health`. It returns 503 when the database is down, so Render stops routing to the instance and restarts it |
| CORS | `CORS_ALLOWED_ORIGINS=tauri://localhost,http://tauri.localhost` (desktop shell); the web app is same-origin |
| Cookies and auth | `Secure`, `HttpOnly`, `SameSite=Lax` cookies and HSTS in production (unchanged); the public URL goes in `APP_BASE_URL` |
| Worker execution mode | Production forces `ANALYSIS_MODE=worker` (P0.1). `ANALYSIS_MAX_MEMORY_MB=1024` and `IMPORT_CONCURRENCY=1` fit the 2 GB `1c-2g` plan |
| Single instance | `numInstances: 1`, no autoscaling, plus the guard below |
| AI | Staging runs `LLM_PROVIDER=fake`: no billable calls until P0.2. Production refuses to start with a real provider unless the key and all four prices are set (P4.5) |

**Single-instance guard** (`server/src/ops/instanceLock.ts`).

- **Why a lock is needed:** the in-process runner, interrupted-import recovery and retention must run in exactly one process per database.
- **How the lock works:** every instance serves HTTP, but only the holder of a session-level Postgres advisory lock runs jobs. The other instances keep new imports queued (`/api/v1/health` reports `jobs: "standby"`) and poll for the lock every 2 s.
- **Deploys:** this fits Render's zero-downtime deploys. The new instance passes its health check in standby, and takes over as soon as the old one exits and its connection closes. Recovery then re-queues anything that was interrupted.
- **Losing the lock connection:** the process exits, and the platform restarts it.

The existing in-process runner is kept. No Redis or queue was introduced, because nothing here requires one.

## 3. Database reliability

| Item | Implementation | Verified |
| --- | --- | --- |
| Automated backups | Render continuous backups with point-in-time recovery on paid databases: **3 days** on a Hobby workspace, **7 days** on Pro or higher (render.com/docs/postgresql-backups). Free databases are not used | **Unverified**: it depends on the Render account. Confirm the recovery window on the database's Recovery page after creation |
| Additional logical backups | `scripts/db-backup.sh`: `pg_dump` custom format, then checks the archive with `pg_restore --list`, then deletes dumps older than `BACKUP_RETENTION_DAYS` (default 14). Run it on a schedule from any machine or CI job with network access to the database | **Verified** locally: backup of `kyc_test` (28 tables) |
| Retention policy | Render PITR: 3 or 7 days (plan). Render dashboard exports: kept 7 days. `db-backup.sh`: 14 days by default. Recommendation for production: weekly `db-backup.sh` to separate storage, kept 8 weeks (`BACKUP_RETENTION_DAYS=56`) | Policy documented |
| Restore procedure | Below; `scripts/db-restore.sh` restores only into an empty database | **Verified** locally: restored into a new database; the row counts of all 28 tables matched the source (identical checksum), 14 migrations present; a second restore into the now non-empty database was refused (exit 3) |
| Migration safety | Before applying anything, `migrate()` refuses badly named or duplicate-numbered files and a database that has migrations the build does not know (an older build over a newer schema). Each migration runs in a transaction with `lock_timeout = 15s`. Every migration from 004 onwards has a rollback script tested in `migrations.test.ts` (now including 014) | **Verified**: `ops.test.ts`, `migrations.test.ts` |
| Connection failures | At start: retry with backoff (10 attempts), then exit with "Database not ready: database unreachable (CODE)". The connection string is never printed. During requests: connection errors become a retryable 503 `SERVICE_UNAVAILABLE` and a `database_unavailable` log line. Health returns 503 | **Verified**: `ops.test.ts` |

`pg_dump` must be at least the server's major version. Locally a version 16 `pg_dump` refused a version 18 server; use the matching client tools.

**Restore procedure**

1. **Render point-in-time recovery:** on the database's Recovery page, choose a time at least ten minutes in the past. Render creates a **new** database; it does not restore in place.
2. **Logical backup:**
   1. Create an empty database.
   2. Run `TARGET_DATABASE_URL=… scripts/db-restore.sh backups/kyc-<stamp>.dump`.
3. Point a staging copy of the service at the restored database, run `npm run db:migrate` (it applies migrations newer than the backup), and run `BASE_URL=<that service> npm run smoke`.
4. Switch production's `DATABASE_URL` to the restored database and deploy. Keep the old database suspended until the smoke test passes on production.
5. Record the incident and the backup used.

## 4. Monitoring and error tracking

| Requirement | Implementation (`server/src/ops/monitor.ts`) |
| --- | --- |
| Production error tracking | Every unhandled 5xx error and every failed import produces one structured `error_report` log line. Each line carries a stable `fingerprint` (error name + first application stack frame + route), the route pattern, the request id, the environment and the version. The message is scrubbed: tokens, API keys, bearer values, URL credentials, email addresses and Postgres row values are removed, and it is capped at 300 characters |
| Structured logs | Pino JSON (unchanged). Request logs carry method, path without query, and status. Cookies and authorization headers are redacted; bodies are never logged |
| Request and job failure visibility | `error_report` (`where: "GET /api/v1/…"` or `"job:import"`), `database_unavailable`, `alert`, `instance_standby` and `instance_lock_acquired` events; `/api/v1/health` shows `queueDepth` and `jobs` |
| 5xx monitoring and alerting | A sliding window counts 5xx responses and failed imports. At `ALERT_5XX_THRESHOLD` (default 10) or `ALERT_JOB_FAILURE_THRESHOLD` (default 3) within `ALERT_WINDOW_MINUTES` (default 5), one `alert` line is logged at error level. If `ALERT_WEBHOOK_URL` (https only) is set, a JSON message `{ text, alert, count, windowMinutes }` is POSTed to it; Slack incoming webhooks accept this format. Each alert kind then stays quiet for one window |
| Health monitoring | Render health checks on `/api/v1/health` (traffic is removed after 15 s of failures, and the instance restarts after 60 s). Add an external uptime monitor on the same URL so a full outage, which stops in-process alerting too, still pages someone |

**Why no Sentry SDK.**

- `@sentry/node` 11.12.0 declares support for Node `>=20.19 <22 || >=22.12 <23 || >=23.2`.
- Its Fastify integration page lists Fastify 3 and 4 only, while this server runs Fastify 5. Adding the SDK would mean depending on behaviour the vendor does not document for our stack.
- The fingerprinted `error_report` lines give grouping and counts through any log service. To use one, add a Render log stream to a log or error-tracking service (for example Better Stack or Datadog).
- Revisit the SDK when its documentation covers Fastify 5.

Nothing is logged that contains credentials, tokens, repository source code or request bodies. `ops.test.ts` asserts this for a thrown error that contains an email address and a session token. The local production run's logs contained no token, email, password, authorization or cookie values (grep counts: 0).
